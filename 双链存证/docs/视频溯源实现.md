# 视频溯源怎么实现：从双指纹到链上验真

> ⚠️ **本文件是「旧版设计」（含 64 bit 感知哈希与副本检测）。**
> 需求已收敛为「只做平台生成视频的创作信息存证」，当前主线实现见 [`创作信息存证.md`](创作信息存证.md)：
> 删掉了感知哈希与 `VerifyPerceptualHash`，只保留 SHA-256 + CID + ownerId + 参数摘要，作者/平台可查。
> 本文件保留下来作为设计演进与「若将来要做副本检测」的参考。

> 面向本仓库现有的合约、链码与 Python 指纹模块，讲清一件事：**一个视频从“平台生成”到“别人拿副本回来查来源”，中间每一步到底存什么、怎么算、怎么判定。**
> 对应代码：
> - 以太坊版：`contracts/VideoEvidence.sol`（已实现反向索引，测试通过）
> - Fabric 版：`chaincode/video-evidence/lib/videoEvidence.js`
> - 指纹：`python/fingerprints.py`
> - 演示：`docs/用Remix跑.md`、`python/demo_e2e.py`

---

## 0. 先分清三个词，否则后面全是糊涂账

| 概念 | 回答的问题 | 靠什么实现 | 本系统的能力 |
| --- | --- | --- | --- |
| **完整性 integrity** | 这个文件有没有被改过？ | SHA-256 | ✅ 强（1 bit 变化即失配） |
| **溯源 / 存在性 provenance** | 这份内容什么时候、由谁、在哪条链上登记过？ | 链上记录 + 时间戳 + 创作者字段 | ✅ 中（依赖写入方身份真实） |
| **归属 / 版权 attribution** | 这个视频在法律意义上是不是你的？ | 身份认证 + 签名 + 法律程序 | ❌ 不解决（只能作为证据之一） |

**“视频溯源”在本项目里 = 证明“这份字节内容在某时间点已被某创作者登记在平台上，且此后未被篡改”，并能在别人拿来副本时判定“它跟登记过的哪一条对应”。**

## 1. 总体数据流（生成 → 存证 → 查询 → 判定）

```
① 生成完成，拿到视频文件
        │
        ├─ ② 算 SHA-256（字节级、精确）
        ├─ ③ 算 64 bit 感知哈希（抗转码）
        ├─ ④ 上传 IPFS → 得到 CID
        └─ ⑤ 生成参数摘要（模型/seed/prompt 哈希）
        │
⑥ 写链（一次交易，字段见 §2）
        │  链上同时建两个索引：
        │    creator → videoId
        │    sha256  → videoId   ← 反向索引，溯源的关键
        ▼
⑦ 之后任何人拿一个视频文件来查：
   算 SHA-256 → 反查 videoId → 取记录 → 用 sha256 / 感知哈希双重比对
        │
        ▼
⑧ 结论分级：完全一致 / 转码副本（大概率同源）/ 未知 / 可疑（元数据对不上）
```

## 2. 存证记录里到底放什么

| 字段 | 类型 | 来源 | 为什么必须有 |
| --- | --- | --- | --- |
| `videoId` | string（链上存 `keccak256(videoId)`） | 平台生成（uuid / `vid_<任务id>_<随机>`） | 业务主键；链上用哈希省 32 字节 |
| `sha256` | bytes32 | 对**文件字节**做 SHA-256 | 精确完整性；也是反向索引的 key |
| `perceptualHash` | uint64（16 位十六进制） | videohash2 | 转码/加水印后仍能判同源 |
| `ipfsCid` | string | Kubo `api/v0/add` | 文件内容定位；内容寻址（同字节同 CID） |
| `creator` | address / 用户 ID | 平台账户体系 | 归属线索（注意：只是“谁被登记为创作者”） |
| `generationParams` / `paramsHash` | string / bytes32 | 模型名、seed、prompt 哈希 | 证明“怎么生成的”；prompt 原文不上链 |
| `recordedAt` | uint64 | **链上 `block.timestamp`** | 可信时间（写入方改不了） |
| `recorder` / `creatorOrg` | address / MSP ID | `msg.sender` / `clientIdentity` | 谁写的这条记录（平台组织） |
| `ledgerTxId` | string | 链码 `getTxID()` | 可追溯到具体交易 |

> **两个“不能省”的设计**：
> 1. 时间取**链上交易时间**，不取客户端传参——否则写入方可自证任意时间；
> 2. 只存哈希/CID，不存视频与 prompt 原文——链上数据不可删除，隐私与合规要求。

## 3. 生成侧：四件套怎么采

```python
# python/fingerprints.py（已实现）
sha256 = compute_sha256(video_path)                 # 精确指纹，毫秒级
phash  = compute_perceptual_hash(video_path)        # 64 bit，几秒（取决于时长）
cid    = upload_to_ipfs(video_path)                 # python/ipfs_client.py
params_hash = sha256_of(json.dumps({"model": ..., "seed": ..., "prompt": ...}))
```

三个坑（都已在代码里处理）：

- `videohash2` 在 Windows 上默认用 symlink → 必须 `do_not_copy=False`；
- `vh.hash_hex` 会丢前导零 → 统一归一化成 **16 位十六进制**（存链前补零）；
- 感知哈希**不能比相等** → 后面用汉明距离 + 阈值判定（见 §6）。

## 4. 存证侧：一次交易写什么、建什么索引

### 4.1 以太坊版（`contracts/VideoEvidence.sol`）

```solidity
// 记录本体
_records[videoIdHash] = Record({ sha256, perceptualHash, recordedAt, creator, paramsHash, ipfsCid, recorder });

// 反向索引（溯源入口）—— 没有它，拿到文件就没法找记录
if (_videoIdBySha256[sha256] == bytes32(0)) {
    _videoIdBySha256[sha256] = videoIdHash;   // first-writer wins
}
```

查询接口：

| 函数 | 用途 |
| --- | --- |
| `getEvidence(videoIdHash)` | 按 videoId 取完整记录 |
| `videoIdBySha256(sha256)` | **按文件哈希反查**（用户上传副本时用） |
| `verifyExact(videoIdHash, sha256)` | 精确比对，返回 `matched` + `recordedAt` |
| `verifyPerceptual(videoIdHash, phash, maxDistance)` | 感知比对，返回 `matched` + `distance` |
| `exists(videoIdHash)` | 是否已登记 |
| 事件 `EvidenceRecorded(videoIdHash, creator, sha256, perceptualHash, ipfsCid)` | 链下监听/建索引 |

**反向索引为什么必须上链**：链上没有“遍历所有记录”的能力（合约不能 for 循环全表）。如果只有 `videoId → 记录`，那么“用户上传一个文件问来源”这事只能靠平台自己的数据库查——那就退化成中心化，链上只剩摆设。

### 4.2 Fabric 版（`chaincode/video-evidence/lib/videoEvidence.js`）

用的是 leveldb 复合键（没有 CouchDB 富查询）：

```javascript
// 写入时建两个索引
await ctx.stub.createCompositeKey("creator~videoId", [creator, videoId]);
await ctx.stub.createCompositeKey("sha256~videoId", [sha256, videoId]);

// 查询
FindVideoIdsBySha256(ctx, sha256) → { sha256, count, videoIds: [...] }
QueryRecordsByCreator(ctx, creator) → { creator, count, records: [...] }
```

> 同一份字节若被登记多次，索引里会有多条；业务上取第一条或最新一条即可（本实现返回全部）。

## 5. 查询侧的四种入口

| 问题 | 用什么 | 输入 |
| --- | --- | --- |
| 这个视频的存证详情？ | `getEvidence` / `ReadVideoRecord` | videoId |
| 这个创作者有哪些作品？ | `QueryRecordsByCreator`（Fabric 复合键） | creator |
| **这个文件是谁的、什么时候登记的？** | `videoIdBySha256` / `FindVideoIdsBySha256` | **文件 SHA-256** |
| 这条记录有没有被改过？ | `GetRecordHistory`（Fabric `getHistoryForKey`） | videoId |

## 6. 验证算法：三种判定与决策树

### 6.1 精确判定（完整性）

```
match = (sha256(当前文件) == 记录的 sha256)
```
一致性极强：改动 1 bit 即失配。**但它有个反直觉的副作用**：用 ffmpeg 转码一次，字节全变 → 精确判定必然 false。所以不能只用它。

### 6.2 感知判定（同源检测）

```
distance = popcount(phash_a XOR phash_b)      # 0~64
match    = distance <= maxDistance            # 默认 10（videohash2 的 15% 阈值）
```

本机实测（合成素材）：

| 变体 | 距离 | 阈值 10 下 |
| --- | --- | --- |
| 重新编码 / 水印 / 改帧率 | 1~2 | 相似 ✅ |
| 缩小一半 | 2（另一段素材 11） | 视素材而定 ⚠️ |
| 裁剪 10% / 换片段 | 11~12 | 不相似 ❌ |

→ **阈值必须用你自己的真实视频校准**，并在报告里写清；`maxDistance` 做成了链上参数就是为了能调。

### 6.3 综合判定（实际业务用的决策树）

```
输入：用户上传的文件 F
1. d = sha256(F)
2. vId = videoIdBySha256(d)
   ├─ vId != 0  → 直接取记录，精确匹配 → 结论「完全一致的正本」
   └─ vId == 0  → 取平台候选集（按 creator / 时间段 / 可选：链下索引）
        3. 对候选记录逐条：
           p = phash(F); dist = hamming(p, rec.phash)
           ├─ dist <= 阈值   → 结论「疑似同源（转码/压缩/加水印）」，附距离
           ├─ 阈值 < dist < 32 → 结论「不确定」，建议人工/特征点复核
           └─ dist >= 32      → 结论「无关」
4. 输出：结论 + 命中的 videoId / txId / 登记时间 / 距离 / 是否精确
```

> 第 2 步里“候选集”怎么来：最干净的方案是把所有记录的感知哈希也做成链上可枚举索引（成本高），或平台侧维护一份只读副本做粗筛、链上只做最终确认。**报告里把这条取舍写出来就是加分项。**

## 7. 归属证明：比哈希更难的那一半

链上记录只能证明“平台在某个时间把这条记录写进去了”，**证明不了“创作者是视频作者”**。补齐归属需要：

1. **创作者签名**：生成完成时，让用户/创作者对 `(videoId, sha256, creator, timestamp)` 做 EIP-191 签名，链上存签名或验签结果；
2. **平台身份可信**：谁有权写记录（`RECORDER_ROLE` / Fabric MSP + AND 背书）；
3. **可信时间**：用链上时间戳，或接第三方时间戳服务；
4. **行业标准**（可选加分）：C2PA / Content Credentials 把“生成模型、编辑历史、签名”打包，本系统可视为其简化版。

## 8. 演示步骤（Remix 版，不需要钱包）

1. 编译部署 `VideoEvidence.flat.sol`（EVM 选 `shanghai`）；
2. 用脚本生成参数：

```powershell
node scripts/hash_inputs.js evidence vid_demo_001 <sha256> <16位感知哈希> 0x<Account #0 地址> '{"model":"demo","seed":42}'
```

3. `recordEvidence(...)` 写入；
4. 验证三个方向：
   - `videoIdBySha256(sha256)` → 反查到 `videoIdHash`（**溯源入口**）；
   - `verifyExact(videoIdHash, sha256)` → `matched: true`；改一字符 → `false`；
   - `verifyPerceptual(videoIdHash, 转码副本十进制哈希, 10)` → 返回 `distance`/`matched`。

本地也可以一条命令跑完全套断言：

```powershell
npm run test:evidence   # 含反向索引、精确、感知、负向路径
```

## 9. 局限（报告「局限」一节应写）

1. **64 bit 感知哈希信息量小**：碰撞与对抗样本空间有限，生产级需更长指纹或关键帧特征（SIFT/ORB）；
2. **裁剪/片段替换不可靠**：实测超阈值，且无法证明“包含关系”；
3. **反向索引 first-writer-wins**：同一内容被多次登记时只认第一个 videoId（可按需改为多值索引）；
4. **IPFS 不保证持久**：无人 pin 会被 GC，需自建 pin 服务或 Filecoin；
5. **链上不可删除**：只存哈希/CID，个人数据与 prompt 原文不上链；
6. **完整性 ≠ 归属**：它不能替代版权登记与法律认定；
7. **平台仍是写入方**：`RECORDER_ROLE`/MSP 是半中心化，审计价值在“不可单方面篡改 + 可追溯”。

## 10. 报告里怎么呈现

- **架构图**：视频 →（SHA-256 / 感知哈希 / IPFS）→ 存证合约/链码 → 索引（creator / sha256）→ 验证方；
- **时序图**：生成完成 → 算指纹 → IPFS → 写链 → 返回回执 → 后续上传验证；
- **判定表**：精确/感知/综合三档 + 实测距离表 + 阈值选择依据；
- **对照表**：本方案 vs 只存 SHA-256 的普通存证（差异在“转码副本仍可溯源”）。

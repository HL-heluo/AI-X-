# 原报告逐节纠错清单

> 用法：对着这份清单改原报告。每条都是「原文 → 问题 → 改成什么」，改完的表述可以直接粘。
> 只列会被追问/会被扣分的点，纯文字润色不在里面。

---

## 第一章 系统架构

**原文**：「前端触发『生成视频』时，先完成 VCR 消耗交易，再异步调用 Fabric 链码写入存证记录。」

**问题**：顺序写对了方向（资金在交付前，存证在交付后），但「先消耗」如果指「直接扣掉」，在生成失败时就要退款——而报告第六章的退款靠 `mint`，与「消耗」不对称。另外「异步调用 Fabric」意味着可能存在「链上没记录但用户拿到视频」的窗口，报告没提怎么兜底。

**建议改成**：

> 前端发起生成后，平台先校验积分并调用合约 `reserve` 将本次费用**托管**到合约（用户需预先 `approve`）。视频生成、转存、指纹计算与 IPFS 上传完成后，平台写入 Fabric 存证；存证成功后调用 `settle` 销毁托管额完成结算。任一步骤失败则调用 `refund` 原路退回，并在本地记录待补偿状态。

---

## 2.1 合约设计

**原文**：`consume(address user, ...)` 由平台持 `CONSUMER_ROLE` 调用 `_burn(user, amount)`；「销毁即代表服务已交付」；「`videoId` 作为事件参数实现一对一绑定」。

**问题**：
1. `_burn` 不需要 allowance，平台可单方面清零任意用户余额 —— 与「用户通过平台兑换 VCR」的授权模型冲突；
2. 「销毁即代表服务已交付」在**消耗发生在生成之前**的流程里不成立：币烧了、服务没交付时，链上只有「交付」的假象；
3. `videoId` 只进事件、不进状态，无法防重复（同一 videoId 可反复扣款）。

**建议改成**：

> 合约采用「用户授权 + 平台托管」的消耗模型：用户先 `approve` 平台额度，平台以 `SETTLER_ROLE` 调用 `reserve`，将金额从用户地址转入合约托管并记录 `videoId` 对应的托管状态；视频交付成功后调用 `settle` 销毁托管额，失败则调用 `refund` 退回用户。该设计使用户保留授权这一否决权，并使「交付后才真正扣款」在链上可验证，同时通过 `videoId` 唯一性检查防止重复扣费。

## 2.2 部署与测试流程

**原文**：「平台向用户 `mint` 100 VCR → **用户调用 `consume`** 生成视频（消耗 10 VCR）→ …」

**问题**：`consume` 有 `onlyRole(CONSUMER_ROLE)`，用户没有该角色，这条流程**在合约上必然 revert**。如果照原文写，答辩现场一跑就穿帮。

**建议改成**：

> 平台向用户 `mint` 100 VCR → 用户调用 `approve` 授权平台 10 VCR → 平台调用 `reserve` 托管 10 VCR → 平台计算指纹、写入 Fabric 存证 → 平台调用 `settle` 销毁托管额 → 查询用户余额为 90、`totalSupply` 为 90。另设失败路径用例：`reserve` 后调用 `refund`，余额回到 100。

> 若保留原版合约（平台直接 burn），测试流程必须写成「平台调用 `consume`」，并在「局限」里主动说明平台具备单方面扣款能力。

### 2.2 附：MetaMask 集成那段怎么写

**原文**：「MetaMask 集成方式：将部署后的合约地址添加至 MetaMask 自定义代币列表，展示 VCR 余额与转账记录。」

**问题**：如果你实际没做钱包集成（比如装不上/用不了 MetaMask），把它写成「已完成」就是虚构实验。答辩时被要求现场演示会直接穿帮。

**建议改成**（二选一）：

> （没做钱包）合约开发使用 Remix IDE 完成编译与交互式验证，运行环境采用 Remix 内置虚拟机（Remix VM）与本地私有链双环境；ERC-20 余额通过合约 `balanceOf` 查询验证。面向终端用户的钱包集成（MetaMask / WalletConnect）属于后续工作，本文未展开实测。

> （做了钱包）通过 MetaMask 添加自定义网络（RPC + chainId）并导入代币合约地址，可展示 VCR 余额与转账记录。

**关键**：交互验证用 Remix VM 完成并截图，这一点在报告里要写清「验证方式」，不要写「MetaMask 已验证」。

## 第三章 Fabric

### 3.1 网络拓扑

**原文**：「背书策略设为 `AND('PlatformOrg.peer', 'AuditorOrg.peer')`，确保每条存证记录需双方共同背书方可写入，体现联盟链的多方信任机制。」

**问题**：只写了收益，没写代价。AND 意味着任一组织 peer 不可用则写入全部失败，链码升级也需双方 approve；此外 `peer` 角色要求 MSP 开启身份分类（test-network 默认开启），换成自建网络要确认 `NodeOUs.Enable: true`。

**建议补一句**：

> 该策略的代价是可用性：任一组织 peer 离线将导致存证写入失败，因此生产环境通常按记录价值分级使用（高价值记录 AND，普通记录 OR），或采用「主链写入 + 审计方只读 + 定期对账」的折中。

### 3.2 链码函数

**原文**：`VerifyVideo(ctx, videoId, sha256)` 「返回布尔值」。

**问题**：fabric-contract-api 的返回值必须是 `string` 或 `Uint8Array`，`return true` 会让 peer 报 `chaincode returned invalid response`。

**建议改成**：返回 JSON 字符串，例如 `{"videoId":"...","match":true,"ledgerTxId":"..."}`；并在正文注明「链码返回值需序列化为字符串，布尔值由调用方解析」。

**另外**：`createdAt` 由客户端传参不可信，应用 `ctx.stub.getTxTimestamp()`。

## 第四章 指纹

**原文 a**：「感知指纹（videohash2）……生成 64 位感知哈希……`str(vh)` 是 64 位哈希的十六进制字符串」。

**问题**：事实错误。`str(vh)` = `'0b'` + 64 个 `0/1`（66 字符）；十六进制是 `vh.hash_hex`，16 位且**会丢前导零**（实测出现过 `0x9f6093609ffc0ff`）。存链上必须归一化为定长 16 位。

**建议改成**：

> `videohash2` 输出 64 bit 感知哈希；`str(vh)` 为 `0b` 前缀的 64 位二进制串，`vh.hash_hex` 为十六进制表示（可能丢失前导零，上链前需补零至 16 位）。

**原文 b**：「对转码、缩放、加水印、改帧率、裁剪等操作具有鲁棒性」。

**问题**：实测裁剪 10% 后汉明距离 11 bit，超过默认阈值 10，判为不相似；「鲁棒」不能一概而论。

**建议改成**（换成你自己的实测数据，这里给格式）：

> 对重新编码、缩放、改帧率、加水印等变体，感知哈希汉明距离为 1~2 bit，可稳定判定为同一视频；对裁剪 10%、截取不同片段等变体，距离达 11~12 bit，超出默认阈值（10 bit），需针对场景调整阈值或引入关键帧特征匹配。

**原文 c**：「局限性：无法验证包含关系，且对反转或旋转超过 10 度的视频不适用。」

**问题**：「10 度」这个精确数字没有出处。实测 5° 是 9 bit、90° 是 36 bit，中间没测。要么自己补测，要么去掉精确数字。

**建议补**：把「64 bit 指纹信息量有限」和「裁剪/片段替换/对抗扰动不可靠」写进局限，并说明生产方案（更长指纹 / 关键帧特征点 / 多模态）。

**原工程细节**：`VideoHash(path=...)` 在 Windows 上默认 `do_not_copy=True` 用 symlink，未开开发者模式会 `WinError 1314`；必须 `do_not_copy=False`，并显式传 `storage_path`。

## 第五章 IPFS

**原文**：「若用户重新上传一个与原始视频完全相同的文件，其 IPFS CID 与 SHA-256 均会匹配链上记录，可据此判定『该副本来自平台』。」

**问题**：逻辑跳跃。哈希匹配只能证明「字节与链上记录一致」（完整性）和「该内容在某个时间点已被写入账本」（存在性），不能证明「这份文件是平台生成、由该用户创作、从平台流出」。

**建议改成**：

> 匹配 CID 与 SHA-256 可证明副本的**完整性**与**时间存在性**（该内容在某时刻已被登记），但不能单独证明**来源归属**。要实现归属证明，需在写入时绑定创作者身份并签名（如平台/创作者对 `(videoId, sha256, creator)` 签名），验证时同时校验签名与哈希。

## 第六章 联动与失败处理

**原文**：「若步骤 2 成功但步骤 3-6 失败，平台需记录『待补偿』状态，由后台任务重试或人工介入退款（调用 `mint` 返还 VCR）。」

**问题**：
1. 「待补偿」没有定义存储、状态迁移、重试上限、幂等键；
2. 退款用 `mint` 会增发，且链上无法区分「退款」与「新充值」；
3. 「生成成功但存证失败」和「生成失败」是两类完全不同的补偿，原文混为一谈。

**建议改成**：

> 平台为每次生成维护三类状态：任务状态、存证状态、资金状态。生成失败 → `refund`；生成成功但存证失败 → 仅重试存证（服务已交付，不退款），存证状态 `evidence_failed`，后台按指数退避重试，超过上限（如 5 次）标记 `evidence_abandoned` 并告警。补偿任务以 `task_id` 幂等，链上以 `videoId` 唯一性防重复托管/退款。

## 第七章 安全与局限

需要补的三点（原文已有方向，但缺论证）：

1. **Gas 量化**：给出一次操作约 45k~65k gas（ERC-20 transfer 量级），按 20 gwei / ETH 3000 美元折算单次 2.7~4 美元，结论「主网高频不可行」，再对比 L2 与批量结算。
2. **完整性 ≠ 归属**（同第五章）。
3. **合规边界**：VCR 定位为不可转让积分、不承诺收益、不做法币兑换与二级市场；合约 `transferable=false` 是这条的工程实现。

## 附：答辩时最容易被问倒的 4 个点（提前准备）

1. 「平台能不能把用户的钱扣走？」—— 原版能，改托管版不能（要 allowance）。
2. 「AND 背书，审计方关机了怎么办？」—— 写入失败，这是可用性代价，要有分级/降级方案。
3. 「感知哈希怎么判定相似？」—— 汉明距离 ≤ 阈值，不是相等；阈值要有实测依据；裁剪会超阈值。
4. 「哈希对上了就能证明视频是我的吗？」—— 不能，只能证明完整性/时间；归属要靠签名与身份绑定。
